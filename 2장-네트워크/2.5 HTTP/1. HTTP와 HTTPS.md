## HTTP (HyperText Transfer Protocol)

> 웹 브라우저와 서버 간 하이퍼텍스트 기반 통신 규약

-   **애플리케이션 계층** 프로토콜
-   **요청(Request) ↔ 응답(Response)** 방식

**기본 구조:**

```
요청: GET /index.html HTTP/1.1
응답: HTTP/1.1 200 OK + 데이터
```

#### 💡HTTP 버전별 특징

| 버전 | 발행 시기 | 주요 특징                                                                                             | 장점 / 단점 |
| --- | --- |---------------------------------------------------------------------------------------------------| --- |
| **HTTP/1.0** | 1996 | \- 요청 시마다 **새 TCP 연결** 생성   <br/>- 요청 단위로 연결 종료   <br/>- 헤더가 간단                                   | **단점:** TCP 연결 반복 → 느림, 헤더 재사용 불가 |
| **HTTP/1.1** | 1997 | \- **Keep-Alive** 지원 → 연결 재사용   <br/>- **파이프라이닝** 지원 (순차적 요청)   <br/>- 캐싱, 호스트 헤더 지원              | **장점:** 속도 개선, 여러 요청 최적화   <br/>**단점:** 순차적 파이프라이닝, 지연 문제 가능 |
| **HTTP/2** | 2015 | \- **멀티플렉싱** 지원 → 하나의 TCP 연결에서 다중 요청/응답 가능   <br/>- **헤더 압축** (HPACK)   <br/>- 서버 푸시(Server Push) 지원 | **장점:** 지연 감소, 효율적 데이터 전송   <br/>**단점:** TCP 기반이므로 **헤드 오브 라인 블로킹(Head-of-Line Blocking)** 존재 |
| **HTTP/3** | 2020 | \- **UDP 기반 QUIC 프로토콜 사용** <br/>- 연결 및 전송 계층 통합, TLS 내장   <br/>- 멀티플렉싱 → 지연 최소화                   | **장점:** TCP 지연 문제 해결, 연결 재시도 빠름, TLS 자동 암호화   <br/>**단점:** 일부 오래된 장치/방화벽 호환성 문제 |

## HTTP/1.0

기본적으로 한 연결당 하나의 요청을 처리하도록 설계.

**▶️ RTT(Round Trip Time, 왕복 시간) 증가**

> **RTT:** 패킷이 목적지에 도달하고 나서 다시 출발지로 돌아오기까지 걸리는 시간

#### ✅ RTT 증가 해결 방법

**1) 이미지 스플리팅:**

> 많은 이미지를 다운받게 되면 **과부하! ▶️** 많은 이미지가 합쳐져 있는 하나의 이미지를 다운받고, background-image의 position을 이용하여 이미지를 표기하는 방법

**2) 코드 압축:**

> 코드 압축: 개행 문자, 빈칸을 없애 코드의 크기를 최소화하는 방법

**3) 이미지 Base64 인코딩:**

> 이미지 파일을 64진법으로 이루어진 문자열로 인코딩하는 방법

**장점:** 이미지에 대해 HTTP 요청을 할 필요가 없음

**단점:** Base64 문자열로 변환할 경우 37% 정도 크기가 커짐

## HTTP/1.1

> HTTP/1.0의 단점(매 요청마다 TCP 연결, 느린 전송)을 개선한 버전. 매번 TCP 연결을 하는 것이 아니라 한 번 TCP 초기화를 한 이후 **keep-alive**라는 옵션을 통해 여러 개의 파일을 송수신할 수 있게 바뀌었다.

> 참고: HTTP/1.0에도 keep-alive가 있었지만 표준화가 되지 않았음

### ✨ HTTP/1.1 주요 특징

**1\. Persistent Connection (Keep-Alive)**

-   TCP 연결을 **요청/응답 후 종료하지 않고 재사용**
-   여러 요청을 **한 번의 TCP 연결로 처리** 가능 → 속도 향상

```
Connection: keep-alive
```

**2\. 파이프라이닝(Pipelining)**

-   클라이언트가 **연속적으로 여러 요청을 한 번에 보내고**, 서버가 순서대로 응답
-   HTTP/2에서는 멀티플렉싱으로 발전

**3\. 무거운 헤더 구조**

-   HTTP/1.1의 헤더에는 쿠키 등 많은 메타데이터가 들어 있고, 압축이 되지 않아 무거움

### HOL Blocking (Head of Line Blocking)

> 큐(queue)의 가장 앞에 있는 패킷이나 요청이 지연되면서, 뒤에 있는 모든 패킷이나 요청이 기다려야 하는 현상

**예시**

1.  HTTP/1.1에서 파이프라이닝 사용 시 하나의 TCP 연결로 여러 요청을 순차적으로 보냄
2.  요청을 A, B, C 순서로 보냈는데 요청 A 처리 중 서버 지연 발생
3.  결과: 요청 B, C는 A가 끝날 때까지 대기 -> **HOL 블로킹**

> **즉, 하나의 패킷/요청이 지연되면 전체 연결 성능 저하**

## HTTP/2

> HTTP/1.x보다 지연 시간을 줄이고 응답 시간을 개선.  
> HTTP/1.1 대비 개선 사항: **멀티플렉싱, 헤더 압축, 서버 푸시**

### 멀티플렉싱

-   하나의 TCP 연결에서 여러 요청과 응답을 동시에 처리 가능
-   HTTP/1.1 파이프라이닝의 **순차적 처리 문제(HOL 블로킹 일부)** 해결
-   각 요청/응답이 독립 **스트림(stream)**으로 전달

### 헤더 압축

-   HTTP/1.x는 매 요청마다 헤더 반복 전송 → 비효율
-   HTTP/2는 **허프만 코딩 압축 알고리즘**을 사용, **HPACK 압축 형식**으로 전송량 줄임 → 속도 향상

> **허프만 코딩?**  
> 문자열을 문자 단위로 쪼개 빈도가 높은 정보는 적은 비트 수를 사용하여 표현하고, 빈도가 낮은 정보는 비트 수를 많이 사용해 표현하여 ▶️ 전체 데이터의 표현에 필요한 비트 양을 줄이는 원리

### 서버 푸시

-   클라이언트 요청 없이 서버가 **필요한 리소스(예: CSS, JS)를 먼저 전송**
-   페이지 로딩 속도 개선
-   TCP 계층 위에서 동작
-   주요 기능:
    1.  **암호화(Encryption)**: 데이터 도청 방지
    2.  **인증(Authentication)**: 서버 신원 확인 (인증서)
    3.  **무결성(Integrity)**: 데이터 변조 확인

> **보안 세션**   
> 보안이 시작되고 끝나는 동안 유지되는 세션. SSL/TLS는 핸드셰이크를 통해 보안 세션을 생성하고 이를 기반으로 상태 정보 등을 공유한다.

## HTTPS (HyperText Transfer Protocol Secure)

-   **HTTP + TLS/SSL 통신 암호화** 프로토콜
-   웹 브라우저와 서버 간 보안 통신을 위해 사용
-   URL 앞에 https:// 로 표시됨

>**즉, HTTPS는 단순 HTTP와 달리 암호화, 인증, 무결성을 제공하는 보안 버전 HTTP**

| **구분** | **HTTP** | **HTTPS** |
| --- | --- | --- |
| 포트 | 80 | 443 |
| 암호화 | 없음 | TLS/SSL 적용 |
| 보안 | 낮음 | 높음 |
| URL | http:// | https:// |

### SSL/ TLS

> 전송 계층에서 보안을 제공하는 프로토콜.  
> 클라이언트와 서버가 통신할 때 SSL/TLS를 통해 제3자가 메시지를 도청하거나 변조하지 못하도록 한다.
>
> 보안 세션을 기반으로 데이터를 암호화 : **인증 메커니즘, 키 교환 암호화 알고리즘, 해싱 알고리즘 사용**

---

> **1️⃣ 인증 메커니즘**  
> 통신 상대방이 정말 신뢰할 수 있는 서버(또는 클라이언트)인지 확인하는 과정

**TLS에서 주로 사용되는 방식:**

**1\. 서버 인증(Server Authentication)**

-   서버가 인증서(Certificate)를 통해 신원 증명
-   인증서 → 공인 인증기관(CA, Certificate Authority)에서 발급
-   브라우저 → 인증서 확인 → 안전한 연결 판단

**2\. 클라이언트 인증(Client Authentication)**

-   서버가 클라이언트를 확인할 때 사용 (은행, 기업 VPN 등)

---

> 2️⃣ **키 교환 암호화 알고리즘**   
> 클라이언트와 서버가 공유 비밀 키(세션 키)를 안전하게 교환하기 위한 알고리즘  
> 목적: 중간에서 도청해도 세션 키를 알 수 없게 함

**주요 방식:**

**1\. RSA:**

-   공개키로 세션 키 암호화

**2\. Diffie-Hellman (DH) / Ephemeral DH (DHE)**

-   임시 키 생성 → 매 세션마다 새로운 키
-   중간자 공격 방지 가능

**3\. Elliptic Curve Diffie-Hellman (ECDHE)**

-   DH를 타원곡선 기반으로 → 더 짧은 키로 높은 보안

---

> **3️⃣해싱 알고리즘 (Hash Algorithm)**  
> 데이터 무결성을 검증하기 위해 해시값(Hash Value) 생성  
> 목적: 데이터 변조 여부 확인

**TLS에서 사용:** 메시지 인증 코드(MAC) 생성

대표 알고리즘: SHA-256

---

#### Cipher Suite (사이퍼 슈트)

> TLS/SSL 통신에서 어떤 암호화 알고리즘을 사용할지 미리 정의한 모음

**프로토콜, AECD 사이퍼 모드, 해싱 알고리즘이 나열된 규약**

```
TLS_AES_128_GCM_SHA256
```

-   TLS→ 프로토콜
-   AES\_128\_GCM → AEAD 사이퍼 모드
-   SHA256 → 해싱 알고리즘

####  AEAD 사이퍼 모드 (Authenticated Encryption with Associated Data)

> 데이터 암호화 알고리즘.  
> AEAD 모드를 사용하면 **암호화 + 인증 코드(MAC) 분리 불필요** → 효율적

**ex.** AES-128\_GCM

## HTTP/3

> HTTP/2의 장점을 계승하면서 TCP 기반 문제를 해결한 버전

-   HTTP/3는 HTTP 프로토콜의 최신 버전 (2020년 표준화)
-   TCP 대신 **UDP 기반의 QUIC 프로토콜** 사용
-   목표: 속도 향상, 지연(latency) 최소화, HOL 블로킹 문제 해결

### ✨ HTTP/3 주요 특징

### **UDP 기반 QUIC 프로토콜 사용**

-   TCP 연결 대신 **QUIC** 사용 → 3-way handshake 과정을 거치지 않아 **빠른 연결 설정**
-   순방향 오류 수정 메커니즘 적용: 전송한 패킷이 손실된 경우, 수신 측에서 에러를 검출하고 수정하는 방식 

> 즉, 열악한 네트워크 환경에서도 낮은 패킷 손실률
